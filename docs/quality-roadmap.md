# План улучшения качества генерации

Цель: повысить качество материалов, создаваемых локальными LLM, на измеримом
наборе примеров без ухудшения времени ответа и стабильности формата.

Первый объект улучшения — навык `chastushki`. Подход должен оставаться пригодным
для последующего применения к другим текстовым навыкам.

## Правила работы

- Меняем за одну итерацию только один фактор: eval, метрику, prompt, параметры
  генерации, модель или этап конвейера.
- Каждое изменение сравниваем с зафиксированным baseline на одном наборе тем.
- Формальные проверки не заменяют человеческую оценку смысла и юмора.
- Изменение принимается, только если оно улучшает целевую метрику и не нарушает
  обязательные ограничения.
- Результаты реальных моделей сохраняем в `data/evals/`, но не коммитим.

## Метрики

Обязательные ограничения:

- ровно две строфы по четыре строки;
- тема сохранена;
- нет повторяющихся строк;
- нет заголовков и пояснений;
- нет грубой лексики и явной бессмыслицы.

Автоматические метрики:

- доля результатов без формальных ошибок;
- доля результатов, сохраняющих тему;
- оценка рифмы;
- оценка ритма по слогам;
- доля повторов слов и строк;
- медианное время генерации одного результата.

Человеческая оценка по шкале 1–5:

- понятность;
- естественность языка;
- ритмичность;
- качество рифмы;
- юмор или выразительность;
- соответствие теме.

Основная итоговая метрика — средняя человеческая оценка среди результатов,
прошедших все обязательные ограничения. До появления достаточной ручной разметки
используем долю прошедших ограничений как промежуточную метрику.

## Этапы

### 0. Зафиксировать baseline

- [x] Сформировать 30–50 тем разных типов: бытовые, технические, абстрактные,
  составные и пограничные.
- [x] Для каждой локальной модели выполнить не менее трёх прогонов каждой темы.
- [ ] Сохранить параметры генерации, автоматические метрики и время выполнения.
- [ ] Вручную оценить одинаковую случайную выборку результатов обеих моделей.

Критерий завершения: есть воспроизводимый отчёт, по которому можно сравнить две
конфигурации без просмотра отдельных удачных примеров.

### 1. Сделать eval надёжным

- [x] Перенести темы в единый версионируемый набор eval-кейсов.
- [x] Исправить `model_eval`: тест должен проверять пороги качества, а не только
  факт получения всех результатов.
- [ ] Добавить агрегаты по модели, параметрам, теме и отдельным типам ошибок.
- [ ] Добавить регрессионные тесты для логики подсчёта метрик.

Критерий завершения: намеренно плохая конфигурация проваливает eval, текущий
baseline измеряется одинаково при повторных запусках с учётом допустимого
стохастического разброса.

### 1.5. Собрать preference-данные

- [x] Определить формат пары: тема, отклонённый вариант, выбранный вариант,
  причины выбора и исходная модель.
- [x] Собрать пилот из пяти реальных ошибок baseline и вручную исправленных
  вариантов.
- [ ] Расширить набор до 50–100 проверенных пар без пересечения с контрольными
  темами.
- [ ] Провести слепую проверку исправленных вариантов человеком.
- [ ] Выбрать из проверенного набора 3–5 контрастных few-shot примеров.

Критерий завершения: все выбранные варианты проходят автоматические ограничения,
человек подтверждает улучшение, а набор можно использовать для проверки метрики,
обучения ранжировщика и последующего LoRA без утечки в контрольную выборку.

### 2. Улучшить локальную оценку кандидатов

- [ ] Заменить сравнение последних букв на оценку рифмы от ударной гласной.
- [ ] Добавить число слогов и разницу ритма между строками.
- [ ] Наказывать повтор слов, одинаковые грамматические окончания и выдуманные
  слова, когда это можно определить надёжно.
- [ ] Проверить вклад каждой метрики отдельно на baseline-наборе.

Критерий завершения: локальный ранжировщик выбирает лучший вариант не хуже
человека как минимум в 75% размеченных пар и улучшает итоговую ручную оценку.

### 3. Улучшить генерационно-редакторский конвейер

- [ ] Сравнить два и четыре независимо сгенерированных кандидата.
- [ ] Передавать редактору конкретные обнаруженные недостатки лучшего кандидата.
- [ ] Запускать редактуру не только при ошибке формата, но и при низкой итоговой
  оценке.
- [ ] После редактуры повторять все проверки и сохранять исходный вариант, если
  исправление его ухудшило.

Критерий завершения: качество статистически лучше baseline, а рост медианного
времени и числа вызовов признан приемлемым.

### 4. Настроить prompt и параметры

- [ ] Сократить дублирующиеся инструкции в `SKILL.md`.
- [ ] Проверить примеры вида «плохой вариант → исправленный вариант».
- [ ] Провести небольшой grid search по `temperature`, `top_p` и числу кандидатов.
- [ ] Для каждой модели хранить выбранную конфигурацию и основание выбора.
- [ ] При изменении публичного определения навыка синхронно обновлять
  `SKILL.md`, `manifest.json` и версию навыка.

Критерий завершения: выбранная конфигурация воспроизводимо выигрывает у baseline
по итоговой метрике и не ухудшает обязательные ограничения.

### 5. Принять решение о модели и обучении

- [ ] Сравнить доступные локальные модели в одинаковых условиях.
- [ ] Оценить компромисс качества, скорости и потребления памяти.
- [ ] Рассматривать fine-tuning только после исчерпания улучшений eval,
  ранжирования, prompt и редакторского прохода.
- [ ] Для fine-tuning заранее подготовить отдельные обучающую и контрольную
  выборки без пересечения с eval-набором.

Критерий завершения: выбор модели или решение об обучении подтверждены цифрами,
а не отдельными примерами.

## Порядок ближайших работ

1. Выполнить этап 0 и получить baseline.
2. Сделать eval из этапа 1 обязательным измерительным контуром.
3. Расширить и проверить preference-набор из этапа 1.5.
4. Улучшать ранжировщик небольшими независимыми изменениями из этапа 2.
5. После стабилизации метрик перейти к этапам 3 и 4.
6. Принимать решение этапа 5 только по накопленным результатам.

## Журнал решений

### 2026-11-07 — автоматический baseline

Конфигурация: 30 тем, три повтора, два кандидата, `temperature=0.8`,
`top_p=0.8`, порог прохождения 80%.

- Qwen 3 8B: 15/90 (16,7%), 373,5 с; медиана 4,30 с, p90 4,94 с,
  максимум 9,00 с; 7 промахов по теме, ошибок запросов нет.
- GigaChat 3.1 10B A1.8B Q4_K_M: 24/90 (26,7%), 853,9 с; медиана
  2,53 с, p90 24,75 с, максимум 146,74 с; 14 промахов по теме, ошибок
  запросов нет.
- Основная автоматическая причина брака: слабая рифма строк 2 и 4 — 54
  результата у Qwen и 36 у GigaChat.
- Ни одна модель не достигла порога 80%. Результаты пока нельзя считать
  окончательным сравнением качества: человеческая оценка ещё не выполнена, а
  текущая метрика рифмы сравнивает только окончания слов.

Решение: сохранить обе модели для следующего этапа. Сначала улучшить отчётность
и локальную метрику, затем повторить автоматический baseline и провести слепую
ручную оценку одинаковой выборки.

После каждой итерации добавляем запись:

```text
Результат автоматической оценки:
Результат человеческой оценки:
Время/ресурсы:
Решение: принять / отклонить / повторить
Следующий шаг:
```
