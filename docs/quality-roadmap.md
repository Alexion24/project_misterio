# План улучшения качества генерации

Цель: повысить качество материалов, создаваемых локальными LLM, на измеримом
наборе примеров без ухудшения времени ответа и стабильности формата.

Первый объект улучшения — навык `chastushki`. Подход должен оставаться пригодным
для последующего применения к другим текстовым навыкам.

## Правила работы

- Пока используем облачные модели; к локальным моделям вернёмся после
  стабилизации eval и метрик качества.
- Меняем за одну итерацию только один фактор: eval, метрику, prompt, параметры
  генерации, модель или этап конвейера.
- Каждое изменение сравниваем с зафиксированным baseline на одном наборе тем.
- Формальные проверки не заменяют человеческую оценку смысла и юмора.
- Изменение принимается, только если оно улучшает целевую метрику и не нарушает
  обязательные ограничения.
- Результаты реальных моделей сохраняем в `data/evals/`, но не коммитим.

## Метрики

Обязательные ограничения:

- ровно две строфы по четыре строки;
- тема сохранена;
- нет повторяющихся строк;
- нет заголовков и пояснений;
- нет грубой лексики и явной бессмыслицы.

Автоматические метрики:

- доля результатов без формальных ошибок;
- доля результатов, сохраняющих тему;
- оценка рифмы;
- оценка ритма по слогам;
- доля повторов слов и строк;
- медианное время генерации одного результата.

Человеческая оценка по шкале 1–5:

- понятность;
- естественность языка;
- ритмичность;
- качество рифмы;
- юмор или выразительность;
- соответствие теме.

Основная итоговая метрика — средняя человеческая оценка среди результатов,
прошедших все обязательные ограничения. До появления достаточной ручной разметки
используем долю прошедших ограничений как промежуточную метрику.

## Порядок ближайших работ

1. Выполнить этап 0 и получить baseline.
2. Сделать eval из этапа 1 обязательным измерительным контуром.
3. Расширить и проверить preference-набор из этапа 1.5.
4. Улучшать ранжировщик небольшими независимыми изменениями из этапа 2.
5. После стабилизации метрик перейти к этапам 3 и 4.
6. Принимать решение этапа 5 только по накопленным результатам.

## Журнал решений

### 2026-11-09 — проверка отбора на сохранённых ответах MiMo

Общая точность ранжирования на 51 preference-паре — 39 из 51. В 20 парах,
где исходник уже нарушал формальные требования, метрика выбрала правку
20 раз. Среди 31 пары, где формальную проверку прошли оба текста, она
совпала с человеком 19 раз, семь раз дала ничью и пять раз выбрала исходник.
Пять старых пар пересекаются с контрольными темами. Этот набор служит
для разработки метрики, итоговое сравнение моделей проводится на отдельных темах.

В двух прогонах MiMo было 32 набора по два кандидата. Среди них 19 наборов
без кандидата, который прошёл бы формальную проверку и сохранил тему,
12 с одним таким кандидатом и один с двумя. Из 12 формально годных
текстов, отклонённых человеком, только у одного была формально годная
альтернатива в том же наборе. Повторный подсчёт с отключением ритма и штрафа
повторов оставил итоговые 5 и 7 формальных проходов без изменений.

Строгий порог для худшей строфы при текущем значении 0,375 отсеял бы
6 из 12 отклонённых человеком текстов и 21 из 51 выбранного preference-текста.
Поэтому сначала проверяем генератор на том же навыке и настройках.
В слепой оценке фиксируем пригодность каждого текста отдельно и считаем
долю пригодных среди всех ответов. Формат, попадание в тему и время
генерации сравниваем отдельно.

### 2026-11-09 — четыре пары для few-shot

Для отдельного эксперимента выбраны четыре пары из
`evals/chastushki_preferences.json`. Во всех четырёх случаях человек выбрал
правку без оговорок. Правки прошли формальную проверку, темы не пересекаются
с контрольным набором и примерами действующего навыка.

- `метел` — «про мартовскую метель». Два четверостишия отделены пустой строкой
  и оформлены обычным текстом.
- `колодец` — «про ведро в колодце». Восстановлены рифмы вторых и четвёртых

- `дрон` — «про дрон над деревней». Вместо «положили яйца в брак» и кота,

  более высокую оценку рифмы, хотя человек выбрал правку.
- `будильник` — «про будильник, который проспал». Будильник звонит поздно,
  как и задано в теме, а вторая строфа развивает ситуацию через петуха.

Для A/B-прогона эти пары задаются через
`MISTERIO_EVAL_FEW_SHOT_TOPICS=метел,колодец,дрон,будильник`.

На MiMo V2.6 Flash сравнили базовый prompt навыка 0.9.0 с тем же prompt
и четырьмя дополнительными парами. Использовали восемь тем из контрольного
набора после исключения примеров навыка, offset 5, два повтора на тему.
Модель и параметры генерации совпадали.

Базовый вариант прошёл формальную проверку в 5 из 16 случаев, вариант
с примерами — в 7 из 16. Шесть ответов прошли проверку только с примерами,
четыре — только в базовом варианте. Один случай прошёл в обеих
конфигурациях, пять провалились в обеих. Ошибок запросов не было.
Медианное время ответа составило 2,43 и 2,20 с соответственно.
Промахов по теме стало четыре вместо одного, ошибок рифмы — три вместо шести.

### 2026-11-08 — пилот модели-судьи естественности

наборе, не меняя генерацию.

— допустимым вариантом. Все шесть меток набора теперь подтверждены.

обнаружила «мышь в приправке», но пропустила «невод свой». Результат MiMo выше
пороговых 80%, однако шести примеров недостаточно для подключения судьи к
runtime; следующий шаг — расширить подтверждённый набор.

Набор расширен до десяти примеров за счёт четырёх ранее проверенных

неестественные образы или глаголы.
